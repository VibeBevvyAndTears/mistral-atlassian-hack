Teams in one organization write for themselves and send to each other. This platform decomposes each team's documents into a graph of topic nodes, catches contradictions before they cross a team boundary, and re-expresses every handoff in the receiving team's own vocabulary — with the original always one click away.

01Overview

Hackathon problem statement

How might AI help multi-disciplinary teams make sense of information, present ideas, align on decisions (avoid decision conflict), and review work more effectively?

1.2 The problem

Teams inside one organization speak different languages — not only literal languages, but different vocabularies, levels of abstraction, and priorities. An engineering spec sent to marketing is technically complete and practically unreadable. A business requirements doc sent to engineering is full of intent and light on constraints.

Four failures compound:

  1. The receiver does the translation work themselves — badly, late, or not at all.
  2. Knowledge fragments across many documents, and nobody notices when doc #7 contradicts doc #2.
  3. Decisions collide silently. Engineering commits to March 1. Marketing plans for March 15. Both are written down. Neither team reads the other's document. The conflict surfaces in week three of execution.
  4. Feedback has nowhere to go. The receiver spots a problem, writes it in a chat thread, and it dies there. Nothing changes in the source of truth.

1.3 The solution

  1. A team's documents are decomposed by AI into a topic node graph owned by that team.
  2. New documents are linked into the existing graph; contradictions are flagged for human review, never silently merged.
  3. At send time, content is checked against the receiving team's graph — catching cross-team decision conflicts before the handoff.
  4. Delivered content is adapted to the receiving team's profile, with the original always one click away.
  5. The receiver reviews it like a code review — inline suggestions anchored to specific nodes. The owning team Lead proposes Accept/Edit (or Rejects); both teams must approve before the graph updates. The proposing team may cancel before apply.
  6. Every generated rendition passes a Rendition Judge before a reader sees it — because adaptation is the one place in the pipeline where no human is checking the AI's work.

Ownership rule — D-1

Every node belongs to exactly one team's space. Members of the owning team can edit. Everyone outside has read-only access. Nodes are never copied between teams. Outside teams influence a graph only by proposing changes that pass the dual-approve gate (D-18).

Approval rule — D-13 / D-18

Resolving a conflict (§5.3) and Accept / Edit / Reject on a suggestion (§5.8) are Team Lead actions. Accept/Edit stages a proposed text and records the owning team's approval — it does not write the graph yet. The graph updates only when both the proposing team and the owning team have approved (D-18). The proposing team may cancel while the suggestion is still open or awaiting approvals (D-19).

Translation ownership — D-3 / D-11

The Adaptation Agent is the only actor that rewrites language. It takes source_team_profile + target_team_profile (including preferred_language and translation_style) and produces one team-level rendition. Individual members do not get personal translations.

4.2 Authoring and ingestion — sender side

Upload file(s) or write text
  → Ingestion (parse, OCR if needed, chunk, keep offsets)
  → Decomposition Agent → topic tree
  → Claim Extraction Agent → atomic typed claims
  → Linking Agent → match against this team's existing graph
       ├─ confident + no contradiction → auto-link, merge claim into node
       └─ contradiction OR low confidence → Review Item
  → Sender resolves queue (accept / edit / reject / keep both)
  → Graph updated, history entries written
Hard rule

Conflicting claims are never auto-merged. The node stays intact; a Review Item is created.

4.3 Sending

Select documents/nodes → choose receiving team → optional cover note
  → Pre-send checklist (deterministic):
       · unresolved internal review items in scope
       · decisions without an owner  ← hard-blocks Send (FR-9.5)
       · dangling references to nodes not included
       · terms flagged as unknown to the receiving team's profile
  → CROSS-TEAM conflict scan against the receiving team's graph
  → Sender revises, annotates, or proceeds with conflicts acknowledged
  → Adaptation Agent renders against Team B's profile
  → [Rendition Judge] fidelity + audience fit
  → Prioritization Agent scores the post
  → Post appears in the A↔B channel
Note

No node ownership changes and nothing is copied. The agent reads across graphs; the graphs stay separate.

4.4 Receiving and review — the code-review model

Team B opens channel → post adapted to Team B's profile
  → toggle "View original"; cross-team conflicts shown prominently
  → ••• menu → View source (which document(s) this came from) / History (right-hand sidebar, no graph UI)

  → Team B reviews:
       · comment on the post, or on a specific item in Package contents
       · propose a SUGGESTION on that item
            - written in Team B's own vocabulary
            - Reverse Adaptation Agent renders it into Team A's profile
            - [Rendition Judge] scores the reverse rendition too
       · post-level action: Agree / Request Changes / Blocked
       · cancel their own suggestion while open or awaiting approvals (D-19)

  → Team A Lead sees suggestions as a review queue against their graph
       · Accept → stages proposed text + records Team A approval (status=awaiting_approvals)
       · Edit   → stages counter-proposal text + records Team A approval
       · Reject → reason required, visible to Team B (terminal; no dual approve)
       · Graph is NOT updated yet

  → Dual approve (D-18):
       · Either party POST /approve until both proposing team and owning team approved
       · Then apply: new node version, history entry, regen, notify
       · Team B may still cancel before the second approval lands

  → After applied (or rejected): Team B marks the thread closed
  → Node change triggers notification back to Team B

05Wireframes

Low-fidelity layouts for the seven screens that carry the product. Each is annotated with the requirement IDs it satisfies, so a reviewer can trace any box back to a line in §6. Colour follows the document legend: AI-generated, human gate, conflict or blocking.

Scope note — no node-level UI

There is no graph canvas and no per-node inspector screen in v1 — the dedicated graph workspace and receiver-graph screens from earlier drafts are removed. The graph itself still exists behind the system — it's the data model in §8, and it still drives linking, conflict detection, and history — it's just never rendered as a visual canvas or exposed as a standalone node page. Instead, a post's ••• menu (§5.6) surfaces View source (which document(s) the post's content came from) and History, which opens a right-hand sidebar listing the change history for that post's nodes. Proposing a change against a specific piece of content also now happens inline in the post detail view, keyed off the item in "Package contents" — there's no separate receiver-graph screen to compose it on.

07Agent architecture

This is not a good fit for a single autonomous agent looping freely over tools. The business flow is a pipeline with clear stages and mandatory human gates. The right shape is an orchestrated pipeline of narrow specialist agents, each with a strict JSON output contract, wrapped around deterministic tools — parsers, embeddings, retrieval, diff.

Agents propose, humans dispose — with one automated judge covering the single stage where no human is looking.

7.4 The Rendition Judge

Why exactly one judge

A judge earns its place where no human gate follows.

Every other stage in this pipeline already ends at a person. A bad decomposition is visible in the node's change history the moment someone looks. A wrong link is one click to delete. A false-positive conflict costs a user one dismissal in a queue they were already reviewing. Adding an automated critic in front of a human who is about to look anyway buys a second opinion nobody asked for, at the cost of a call, a prompt to maintain, and a way to be wrong.

Adaptation is the exception. The rendition goes straight to the receiver's screen and is trusted as if it were the original. If it drops a constraint or invents a date, nobody catches it — that's the whole premise of the product. So that stage gets a judge, and nothing else does.

Verdict shape

{
  "fidelity": {
    "verdict": "pass | fail",
    "invented_facts": [{"text": "...", "span": [120, 156]}],
    "dropped_facts":  [{"text": "...", "source_span": [45, 89]}],
    "altered_values": [{"original": "March 1", "rendered": "early March"}],
    "rationale": "..."
  },
  "audience_fit": {
    "verdict": "pass | weak | fail",
    "jargon_appropriate": true,
    "detail_depth_match": "too_dense",
    "unexplained_terms": ["..."],
    "rationale": "..."
  },
  "overall_confidence": 0.86
}
FailureAction
Fidelity failRetry once with the critique → still failing, show the original with a warning banner
Audience fit failRegenerate once with the critique → still failing, ship with a low-confidence badge
Audience fit weakShip, badge it, log for the eval set

Fidelity and fit stay separate dimensions — collapsing them into one score produces a mushy verdict that fails at whichever it weights less — but they share one call, because they read the same two inputs and splitting them doubles cost on the hottest path in the system.

Design rules

  1. Separate call, fresh context. The judge never sees the adaptation agent's reasoning — only the original, the output, and the profile. Self-grading in the same context inflates scores.
  2. Structured verdict, not a number. Every failure cites the span that failed, which makes it debuggable and drives the UI.
  3. Never the sole gate on high-stakes. The judge can badge a rendition low-confidence; it cannot approve a conflict resolution or apply a suggestion.
  4. Log every verdict alongside the rendition, so a confidence indicator traces back to a specific rubric result.

7.5 Documented fallback — not built

If conflict detection proves noisy

The cheapest fix is a second-opinion pass on high-severity conflicts only: same Conflict Agent, stricter prompt, one extra call, asked to distinguish a genuine contradiction from a temporal update or a scope difference. Not built for v1 — a human gate already follows conflict detection, so a false positive costs a dismissal, not a wrong outcome. Recorded so it doesn't need rediscovering if the false-positive rate climbs.

RiskMitigation

10Resolved decisions

IDDecision
D-1Node ownership. Every node lives in exactly one team's space. Members of that team edit; everyone outside is read-only. Nodes are never copied or synced between teams.
D-2Cross-team conflict detection reads, never copies. The agent queries the receiving team's graph at send time; only the conflicting claim is surfaced.
D-3Adaptation is per-team, not per-user. The team profile is the LLM parameter set. One cached rendition per content version × profile version.
D-4Post-send changes notify. The receiving team is notified when a delivered node changes; the post gets an "Updated" badge and the rendition regenerates.
D-5Data-sensitivity concerns deferred. Commercial LLM APIs assumed.
D-6Full feature scope. No hackathon cut; §9 sequences the build rather than trimming it.
D-7Receiver feedback is code review. Suggestions are proposals against specific nodes, reverse-adapted into the sender's vocabulary, staged by the owning Lead, applied only after dual-team approval (D-18), credited in node history, cancellable by the proposer before apply (D-19), and closed by the proposing team after apply/reject.
D-8One runtime judge. A judge earns its place only where no human gate follows — which in this pipeline means adaptation alone. Fidelity and audience fit are two dimensions of one verdict, one call.
D-9Team profile schema (OQ-1). TeamProfile(id, team_id, version, identity_label, identity_description, translation_style, expertise_level, tone, detail_depth_default, responsibilities[], jargon_known[], jargon_must_explain[], preferred_language, created_at) — Ryu's proposed fields, extended with the jargon lists and preferred language needed to back the W1 form and the judge's fit rubric. See §8.
D-10Conflict detection does not re-run on receipt (OQ-4). It runs exactly twice — intra-team on ingest, cross-team at send — because the send-time scan already checks against the receiver's graph before the content ever arrives; a third pass on the receiving side would be redundant.
D-11Both translation modes in scope (OQ-5). V1 supports literal cross-language translation and same-language jargon adaptation, selected per team via translation_style and preferred_language on the Team Profile.
D-12Channels are one-to-one (OQ-6). A Channel connects exactly two teams; confirmed against the existing Channel(id, team_a, team_b) model.
D-13Lead approval required (OQ-7). Resolving a conflict and Accept / Edit / Reject on a suggestion are Team Lead actions. Members can raise, discuss, and propose. Accept/Edit stages a proposal and records the owning team's approval — it does not alone write the graph (see D-18).
D-14Internal resolutions surface via History only (OQ-8). The receiver can see how the sender resolved an internal conflict, but only by opening the post's History sidebar (§5.6) — never surfaced by default on the post body.
D-15Suggestion scope is package-bound (OQ-9). A receiver's suggestion may only target a node included in the package they actually received, not the sender's graph at large.
D-16Cross-team agent reads broadly, UI reveals narrowly (OQ-3). The Conflict Agent may query all of Team B's graph when scanning Team A's outgoing package — restricting it to only what B has already shared would miss most real collisions. The privacy boundary is enforced downstream instead: the agent's output schema carries only the single matched claim, and no code path passes raw cross-team graph results to a UI or API response (consistent with D-2 and the §7.6 guardrail). Revisit if this reasoning doesn't hold up under review.
D-17Channel feed has no right-rail chrome for open items or priority explain (§5.5). "Open on you" is a notification concern (bell + optional toast + Views lists). "Why this order" is an AI info affordance beside Priority sort — the factor text is fixed (FR-14.2), so it must not consume a permanent column.
D-18Dual-team approve before apply. After the owning Lead Accepts or Edits, status is awaiting_approvals with proposed_text staged. Both the proposing team and the owning team must record approval (via SuggestionApproval). Only then is the node mutated, version bumped, history written, and rendition regen enqueued. Reject skips this path.
D-19Proposer may cancel before apply. The proposing team can cancel while status is open or awaiting_approvals. Status becomes cancelled; the owning team is notified; no graph write. Cancel is not available after applied / rejected.
